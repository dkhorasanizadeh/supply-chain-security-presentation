Attacks reached the chain long before npm existed.

2002: trojaned tarballs of OpenSSH, Sendmail, tcpdump. The payload hid in the Makefile and fired at build time.

2003: the Gentoo Portage mirror was rooted. About 20 users synced in the hour before shutdown.

2008: Debian OpenSSL — no attacker at all. A packaging edit made key generation predictable for nearly two years.

A compromise upstream can reach everyone who builds or deploys the resulting artifact.

▶ Next · Internal developers: someone with commit access can hide a backdoor in a normal change. The release pipeline then builds and distributes it.

▶ Next · Malicious developers: a dependency can run attacker code during installation, build, or runtime. Adding it brings that code into our chain.

▶ Next · Compromised CI: control of a runner, build tool, or workflow lets an attacker inject code into the output while reviewed source stays clean. If CI can sign and publish, it can ship the altered artifact as an official release.

▶ Next · Stolen tokens: a publishing token lets an attacker upload a malicious package or image as the trusted publisher. Consumers can then pull it through their normal update process.

▶ Next · Zero days: a shipped dependency can contain an unknown flaw that an attacker later exploits at runtime. This is inherited vulnerability risk; it does not by itself mean the release was tampered with.

The first defense: checksums along the files

But where does it fail?

A checksum is a fingerprint of the file's bytes. Compute it after downloading and compare it with the published value; a mismatch means the file changed or the download was corrupted.

A PGP signature authenticates the checksum list. Verify it with a public key you already trust, then check the file against that list. Replacing the file and list alone cannot forge the signature.

▶ Next · Reveal: But where does it fail?

The weak point is the reference value. If an attacker can replace both the tarball and its unsigned checksum on a mirror, the malicious file still passes the check.

A valid signature does not prove the software is safe. A compromised build or stolen signing key can still produce a signed malicious release.

SBOM: knowing what's inside

The answer to “What does it contain?”

my-app:1.4.2 (the artifact, by digest)
├── openssl 3.0.2          included in
│   └── zlib 1.2.13        included in
├── pg-driver 3.3.2        built by a CI run
└── debian:12-slim         contains (base image)
    └── glibc 2.36         included in

BOMs started in manufacturing as lists of parts.

An SBOM maps our dependencies, their versions, and their dependencies.

When a dependency has a flaw, find the affected releases through their SBOMs.

Build the inventory incrementally by combining dependency SBOMs and preserving their links.

Keep an SBOM with each build's digest to track changes.

Provenance: evidence you can check

The answer to “where did it come from?”

Provenance is a build record tied to one artifact by its digest.

Subject: match the recorded digest to the exact artifact we plan to deploy.

Build definition: identify the source, inputs, and process used to build it.

Run details: identify the builder and the specific build execution.

Authenticate the record using a trusted signer before trusting its contents.

Compare the builder, source, and build parameters with our deployment policy.

SLSA: a shared framework for build trust

Supply-chain Levels for Software Artifacts

SLSA, pronounced “salsa,” gives us shared requirements for protecting the software supply chain.

Source track: preserve revision history and record who changed the code and which controls were followed.

Stronger source levels enforce those controls and require two trusted reviewers.

Build track: record the source, inputs, and builder so we can check how an artifact was produced.

Stronger build levels authenticate provenance and harden the build platform against tampering.

The build produces the artifact we verify.

Source and build levels are assessed separately.

SLSA does not prove that the software is free of vulnerabilities.

Scanning: trust decays, so recheck it

Same digest, updated vulnerability data

Signatures, SBOMs, and provenance describe an artifact or its build at a point in time.

A new vulnerability advisory can change our risk assessment without changing the artifact.

Rescan the exact digest or its SBOM against updated vulnerability data.

A clean scan means no known matches within the scanner's coverage.

Recheck deployed artifacts on a schedule and when relevant advisories appear.
